# CLAUDE.md — Nastrój

Zasady pracy Claude w tym repozytorium. Repo jest publiczne (ten plik też), więc bez danych osobowych.
Przy rozbieżności z kodem źródłem prawdy jest kod i testy — wtedy popraw ten plik (sekcja „Utrzymanie”).

## Kontekst

- Właściciel: Jacek (product owner, wcześniej 15 lat programista). Komunikacja po polsku, zwięźle, rzeczowo.
- Cel: prosta, szybka PWA na Androida do oceny nastroju i energii 3× dziennie, zarządzania energią
  metodą „energy accounting” i śledzenia leków — z myślą o osobach neuroatypowych (ADHD, autyzm) w Polsce.
- „Nastrój” to nazwa robocza. Interfejs: tylko polski (wersja angielska jest planowana — nie wprowadzaj
  tłumaczeń ani mechanizmu i18n bez decyzji autora).
- Ton tekstów: ciepły, nieoceniający; dopuszczalny luźny/kolokwialny język (decyzja autora).

## Proces zmian

gałąź → commit (testy przed każdym commitem) → push (GitHub Actions „Testy”) → PR → kopia testowa (artefakt) → merge na prośbę autora.

1. **Gałąź** od aktualnego `main`, nazwa opisowa po polsku (np. `dzis-os-doby`).
2. **Testy przed każdym commitem:** `node tests/pokrycie.mjs`. Przy czerwonych testach nie commituj: napraw kod,
   a jeśli zmiana zachowania jest zamierzona, popraw test i powiedz o tym wprost.
3. **Commit** jako `jab-jab-coder` (autor i e-mail jak w `git log`). Wiadomość: `Obszar: co się zmieniło`
   (np. `Energia: …`, `Dziś: …`), w treści punkty. Trailer `Co-Authored-By` dozwolony;
   **bez** linii `Claude-Session` i bez linku do sesji Claude.
4. **Push**, potem sprawdź wynik GitHub Actions dla tego SHA i raportuj jedną linią:
   `Testy: ✓ 192/192 · storage 113/113 · CI ✓` (liczby z bieżącego przebiegu). Przy błędach — lista nieudanych testów.
5. **PR** tylko na polecenie „zbuduj PR”. Bez niego zapytaj, czy przygotować PR, czy zostać przy commicie na gałęzi.
   - Tytuł: `Obszar: opis (vNN)`.
   - Opis: co się zmieniło · `## Dane` (nowe klucze/pola albo „bez zmian”) · `## Wersja` · `## Testy` · `## CLAUDE.md`.
   - **Bez** linku do sesji Claude. Jeśli środowisko samo dopisze stopkę z linkiem do sesji, usuń link
     (`gh api -X PATCH …/pulls/NN -F body=@plik`). Ogólna stopka „Generated by Claude Code” bez linku może zostać.
6. **Kopia testowa (artefakt)** do ręcznego testu UI: wszystkie pliki aplikacji z gałęzi **bez `sw.js`**,
   tytuł strony `Nastrój test PR NN`. Ma osobną, pustą pamięć — autor importuje do niej swoją kopię JSON.
   Testy automatyczne nie zastępują tego kroku i go nie zmieniają.
7. **Merge** tylko na prośbę autora.

## Wersja service workera (`VERSION` w `sw.js`)

- Podnoś **raz na PR** (nie przy każdym commicie), osobnym commitem `sw.js: VERSION nastroj-vNN`.
- Dotyczy PR, które zmieniają pliki serwowane telefonowi (lista `SHELL` w `sw.js`). PR tylko z `tests/`,
  `README.md`, `CLAUDE.md` czy `.github/` nie podbija wersji.
- Nowy numer = najwyższy z `main` i otwartych PR + 1 (równoległe gałęzie nie mogą dostać tego samego numeru).
- W odpowiedzi i w sekcji `## Wersja` opisu PR podaj: nową wersję, poprzednią z datą jej commita
  i różnicę czasu (minuty/godziny), np. „nastroj-v51 (poprzednia v50 z 23.10.2026 23:24, 18 min wcześniej)”.
  Data poprzedniej (commit, który ją wprowadził): `git log --format='%h %ci' -S"'nastroj-vNN'" -- sw.js | tail -1`
  (w płytkim klonie najpierw `git fetch --depth=300 origin main`).

## Technologia

- PWA: czysty HTML/CSS/JS. Bez frameworków, builda, npm, backendu, bibliotek z CDN i zapytań do zewnętrznych serwerów.
- Wykresy: ręczne SVG.
- Testy: Node 22, wbudowany `node:test`, bez npm (`tests/README.md`).

| Plik | Rola |
|---|---|
| `index.html` | szkielet, nawigacja dolna, kolejność skryptów |
| `styles.css` | motyw, karty, wykresy, style gier |
| `app.js` | rdzeń: oceny, Tydzień/Miesiąc, ustawienia, przypomnienia, eksport/import, start aplikacji |
| `energy.js` | moduł Energia (energy accounting, plan, badania, strategie, stoper) |
| `leki.js` | moduł Leki (format danych opisany na początku pliku) |
| `samouczek.js` | samouczek „Pierwsze kroki” |
| `komplementy.js` | słownik komplementów |
| `dzik.js`, `tama.js`, `animals-together.js` | ukryte widoki-zabawy |
| `sw.js` | offline (stale-while-revalidate) + przypomnienia (periodic background sync) |
| `manifest.webmanifest` | instalacja, ikony, skrót „Stoper” (`./?widok=stoper`) |
| `pobierz.html` | strona instalacji dla znajomych |
| `icons/` | ikony, mordki zwierząt, QR |
| `tests/`, `.github/workflows/testy.yml` | testy i CI |
| `tests/dane-testowe/generuj.mjs` | generator przykładowych danych do ręcznego testu UI (nie test; wynik w `.gitignore`) |

- **Kolejność skryptów** (wszystkie `defer`, wspólny zakres globalny):
  `komplementy.js → energy.js → leki.js → dzik.js → animals-together.js → tama.js → samouczek.js → app.js`.
  `app.js` na końcu wywołuje m.in. `energyInit()`, `medsInit()`, `navInit()`, `tutMaybeStart()`.
- **Nowy plik JS aplikacji** dopisz w 4 miejscach: `index.html` (kolejność), `SHELL` w `sw.js`,
  `APP_FILES` w `tests/harness.mjs`, `APP` w `tests/pokrycie.mjs`. Nowy plik statyczny (CSS, ikona) — do `SHELL`.
- **UI:** każdy widok to `renderX()` budujące HTML. Zdarzenia delegowane na `document` w `app.js`
  (`click`/`input`/`change`) przez atrybuty `data-act` — nowe akcje dopisuj tam, bez osobnych listenerów.
- **Ukryte widoki** (dzik, tama, animals-together): stan tylko w pamięci, nigdy w localStorage.

## Testy automatyczne

- `node tests/pokrycie.mjs` — wszystkie testy + sprawdzenie, że każde miejsce w kodzie czytające lub zapisujące
  localStorage wykonuje co najmniej jeden test. Pojedynczy plik: `node --test tests/leki.test.mjs`.
- Każda nowa lub zmieniona operacja na localStorage dostaje test w `tests/`.
- Nowy **klucz danych**: eksport/import (`energyExport()`/`energyImport()` albo `medsExport()`/`medsImport()`),
  `EXPORT_FIELDS` w `tests/harness.mjs`, przykładowe dane w `tests/fixtures/export-v2.json`.
- Nowy **klucz techniczny**: `TECHNICAL` w `tests/contract.test.mjs` z uzasadnieniem, dlaczego nie trafia do kopii.
- Nowe **pole w zapisywanym obiekcie**: `FIELDS` w `tests/contract.test.mjs` + opis formatu w `README.md`.
- Testy nie obejmują wyglądu, wykresów SVG, gier, service workera ani telefonu — do tego jest kopia testowa.
- **Dane do ręcznego testu:** `node tests/dane-testowe/generuj.mjs` → `dane-testowe.html` (wczytanie na lokalnym serwerze)
  i `dane-testowe.json` (import, np. do kopii testowej). Nowy klucz lub pole danych — dopisz też do generatora.
  Opis: `tests/README.md` → „Dane testowe do ręcznego testu UI”.

## Dane — zasady nienaruszalne

- Wszystko zostaje na telefonie: localStorage (+ stan przypomnień dla service workera w Cache Storage
  `nastroj-state`). Nic nie opuszcza urządzenia, żadnej analityki.
- **Klucze** — źródło prawdy: `EXPORT_FIELDS` (dane, trafiają do kopii JSON) i `TECHNICAL` (techniczne).
  Obecnie: dane — `nastroj.` + `entries.v1` (oceny `{v,t,e}`), `settings.v1`, `activities.v1`, `energy.v1`,
  `plan.v1`, `surveys.v1`, `strategies.v1`, `records.v1`, `meds.v1`, `medpacks.v1`, `medlog.v1`;
  techniczne — `schema`, `backup.pre-v2`, `notified.v1`, `compliment.v1` (nieużywany), `compliment.v2`.
- Zgodność wstecz: nigdy nie zmieniaj znaczenia istniejących pól ani kluczy — tylko dodawaj nowe.
  Klucz raz dodany nie znika z kodu (pilnuje `contract.test.mjs`).
- Eksport JSON `version: 2` zawiera wszystkie klucze danych; import przyjmuje pliki v1 i v2.
- Import ma tylko dopisywać. **Obecne odstępstwa — do decyzji autora** (opis w `tests/README.md`):
  ocena z tej samej pory i dnia oraz czynność/lek o tym samym `id` są zastępowane wersją z pliku;
  ustawienia są w eksporcie, ale import ich nie przywraca. Nie zmieniaj tego bez decyzji.
